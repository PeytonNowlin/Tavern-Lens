## Acquisition and validation priorities

1. **Add turn-conditioned purchasing priors.** The Firestone card-by-turn endpoint is reachable in the new investigation; preserve exact turn, card ID, sample counts and comparison placements. Add a dedicated data-store/model adapter and pass the selected snapshot through `AdvisorRequest`. Use it as evidence for supported purchases, with uncertainty for sparse rows, rather than as a substitute for recruit semantics. The [strategy-source investigation](advisor-strategy-data-sources-2026-10-02.md) records the live schema, counts and source links.
2. **Use rich fields from existing feeds.** Current hero aggregates already carry turn-level board-strength/combat summaries that `FirestoneHeroStat` does not retain. Current trinket records carry MMR breakdowns that `TrinketStats.Entry` drops. Preserve those fields with explicit statistical scope before adding another marginal-placement provider. Hero summary means without per-turn sample distributions do not establish accurate quantiles or a calibrated weak-board threshold.
3. **Expand build-specific dependencies and structured effect coverage.** HSBG Cards' related entities and HearthSim's raw `CardDefs.Bacon` tags can expose generated tokens and activation/dependency metadata. Use these to preflight coverage and generate reviewed rules, including the Lionfish–Fishbait relationship. Full effect execution still belongs to the planner. The [effect investigation](advisor-effect-data-sources-2026-10-02.md) distinguishes existing metadata, extra dependencies, and reusable code.
4. **Export our own action trajectories.** The current logs contain action markers that the bounded displayed-decision archive does not label. Join packet-level legal options, pre-action visible state, outgoing player selection and confirmed effects; add advisor publication time/fingerprint and explicit adherence. This is a more concrete training/evaluation source than a model repository without published expert trajectories. See the [decision-dataset investigation](advisor-decision-datasets-2026-10-02.md).

The modern `hsrl2` code in [HSBRSIM](https://github.com/Gallo13th/HSBRSIM) provides concrete Lionfish and Living Prison activation scripts/tests, making it a useful semantics/reference lead for our exact gaps. Its separate older RL wrapper does not establish a correct current full-game trainer; use the [dataset investigation](advisor-decision-datasets-2026-10-02.md) for coverage and license limitations. Independently validate any adopted behavior against client-build-matched captured actions.

For implementation, first restore coverage for the already-observed Clock/Fortify cases and validate missing activation transitions; acquire the new priors in parallel so they can inform plans whose effects are actually supported.

Independent providers and full recruit engines belong in a pilot/reference tier until freshness, schema, coverage and reuse are verified. BattlegroundsHelp's community source is independent but the checked last-patch feed is only 43 solo games; its percentile buckets describe its own participants. DeepBattler's public model/training code does not establish a current expert-action corpus or measured improvement. Neither should displace a working current source based on a promising README alone. The [expert-source check](advisor-expert-knowledge-sources-2026-10-02.md) also found real curve/commitment material but no verified fresh independent structured feed: the curvesheet still labels patch 29.6.2, Fantasy Warden labels 35.2.2, and Jeef’s former site redirects to the already-used HSReplay source.

## Integration requirements

Keep three contracts distinct: build-specific card metadata and observed counters; supported recruit/combat semantics; and population/expert strategy evidence. Each source adapter should capture provider, source update time, client build or patch where supplied, population, independent sample count, metric meaning and access provenance in the serialized advisor request. Requests must replay without fetching newer data.

For effect coverage, retain an explicit reason for each omission (`missingDefinition`, `missingRelatedEntity`, `missingObservedCounter`, `unsupportedTransition`, `unresolvedRandomChoice`). Do not present all of these as one generic missing-data problem. A build-wide coverage inventory should check the active pool and surface newly changed definitions before another live match exposes them. Exact-definition gates protect old replay policies; resolve supported state transitions before widening simulation coverage.

For statistics, use turn-conditioned card outcomes and hero-specific leveling as modest priors alongside current board, gold, health and surviving scenarios. Final-board placement is a destination signal, not a causal purchase label. Prior data should not unblock an action whose legal effect is unknown.

For learning data, preserve timestamped before-action states and observed player actions, matching advisor advice and later outcomes. The newest saved compressed Power replay already contains 117 `SendOption` markers, 22 `SendChoices` markers and 12,495 `DebugPrintOptions` markers. These are line-marker counts, not deduplicated player-action counts. Current [PowerLogParser](../../Sources/PowerParser/PowerLogParser.swift) handles offered entity choices and server-chosen entities but does not emit the outgoing `SendOption`/normal option packets needed for action labels. Current diagnostic decisions lack per-decision timestamps/action labels and can be evicted before match completion. This local data can supply reliable regression and expert-review cases; it does not reveal counterfactual placement by itself.
